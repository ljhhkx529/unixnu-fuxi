## The cause: the always-on processor's window was at the wrong address

`package/FuxiModemProbe.cpp`'s `kAossBase` was `0x00c30000`. The board's always-on processor is at
`0xc300000`:

| source | what it says |
| --- | --- |
| upstream `arch/arm64/boot/dts/qcom/sm8550.dtsi:4682` | `aoss_qmp: power-management@c300000 { reg = <0 0x0c300000 0 0x400>; }` |
| the CAF live device tree | `power-controller@c300000`, reg `0xc300000` of `0x400` |
| `facts/audio/binding.toml` | `aoss_base = { value = 0xc300000, ... }` |
| `package/FuxiAdspProbe.cpp:1155` | the ADSP probe maps `p.aoss_base`, which is that same `0xc300000` |

So the modem probe was mapping a window 1 MiB below the real one — an address nothing else on the
board uses. With one hex digit missing, the two candidate addresses read very alike, which is why
the mistake survived several rounds.

## How the mistake was found

The bring-up used to stop with the last line being `pas 38 step 0 answers 0/0` and no further
output. A step marker was put in front of every call, and the QMP handshake was instrumented:

```
FUXI_MODEM: step: the mailbox to the always-on processor
FUXI_MODEM: the mailbox descriptor before the handshake
```

and nothing after it. The descriptor was read word by word with each word printed before the next
one was read, so the last word to arrive would name the read that faulted — and the kernel panicked
before any word arrived. The panic was the reading: the mapped address was not a device window at
all.

The fix is one constant. With the address right, the same descriptor reads out cleanly, and it is
exactly the descriptor upstream expects:

```
FUXI_MODEM: the mailbox is at 0xfffffff8ddcae000 of 1024 bytes
FUXI_MODEM: the descriptor word 0 is 4d41494c      <- QMP_MAGIC
FUXI_MODEM: the descriptor word 1 is 00000001      <- QMP_VERSION
FUXI_MODEM: the descriptor word 3 is 0000ffff      <- the AOP's link state: up
FUXI_MODEM: the descriptor word 9 is 0000ffff      <- our link state: up
FUXI_MODEM: the descriptor word 11 is ffff0000     <- our channel state: down
FUXI_MODEM: the descriptor word 13 is 000002d8     <- our mailbox size: 728 bytes
FUXI_MODEM: the descriptor word 14 is 00000128     <- our mailbox offset: 296
```

Word 0 is `QMP_MAGIC` (`0x4d41494c`, "mail") and word 1 is `QMP_VERSION` (1), both as
`drivers/soc/qcom/qcom_aoss.c` defines them. Words 13 and 14 are the mailbox size and offset, and
the mailbox the port used (`box 296 of 728 bytes`) is the one the descriptor names.

## The other two defects this round found

**The handshake was never started.** `qcom_qmp_step` is what writes the first half of the handshake
out and rings the doorbell, so a caller that only waits for an interrupt waits for an answer to a
question it never asked. The old `stepQmpOpen()` called `qcom_qmp_step` only from the interrupt
handler. It now steps the state machine in a loop and waits for each answer.

**Every "bounded" wait was unbounded.** `waitEvents()` ignored the result of `assert_wait_timeout`,
so on a timeout it fell through to `thread_block(THREAD_CONTINUE_NULL)` and never returned. The
same defect was in `package/FuxiAdspProbe.cpp:562`; both are fixed to check the result and take the
wait off the thread, so a step that waits for the always-on processor or for the modem's doorbells
can give up and report.

## What the round does not prove

- **`glink_up` is still 0.** The GLINK edge to the modem is not up, so the QRTR/GLINK data plane
  is not established. Stage 9 means the modem was started and answered, not that the data path
  works.
- **The modem's SMP2P ready value is 4**, which is the item id's own encoding; the port has not yet
  checked the ready bit against upstream's `q6v5_ready_interrupt`.
- **No SIM was read.** The task was the baseband being recognized, and that is what this round
  measured. Reading slot 1 is the next step, and it needs the GLINK data plane.
- The RF is still off, as blocker B6 requires.

## The order that worked

The order is upstream's (`drivers/remoteproc/qcom_q6v5_pas.c`, `qcom_pas_start`):

```
the device tree blob's metadata   -> INIT_IMAGE, accepted (0/0)
the device tree blob's segments   -> copied into the blob's carveout
the mailbox to the always-on processor -> the handshake opens
the always-on processor's load state -> "{class: image, res: load_state, name: modem, val: on}", answered 0
the device tree blob's reset       -> AUTH_AND_RESET, accepted (0/0)
the modem image's metadata         -> INIT_IMAGE, accepted (0/0)
                                    -> MEM_SETUP, accepted (0/0)
the modem image's segments         -> 31 segments copied
the modem image's reset            -> AUTH_AND_RESET, accepted (0/0)
```

The load state message goes to the always-on processor before the blob's reset, which is where
upstream puts it and where the reference port for the same modem (`hakios.mpss.c`, `step_start`)
puts it too. The earlier round that reordered it and saw a regression was measuring the wrong thing:
the run was already stopped at the mailbox, so the difference it showed was not about the order.
